# The repository map — where everything is, and what changes together

| | |
| --- | --- |
| **What** | The coupling map of this repository: where each kind of artefact lives, and — the part no directory listing can tell you — what *else* must change when you change one. Plus which couplings CI enforces and which run on discipline |
| **Who** | Anyone changing this repository. No prior knowledge assumed; junior-safe by intent |
| **When** | Against the tree as of the pin in `settings/managed-settings.json`; the couplings themselves change rarely |
| **Where** | This repository only — host-side procedure is [`OPERATIONS.md`](OPERATIONS.md) |
| **Why** | The main defect class in a repository like this is a coupling missed: a script whose exec bit never reaches git, a hook the Makefile does not stage, a count that goes stale in several documents. The couplings exist whether or not they are written down; this page makes them visible in one place |
| **Status** | In force. Maintained with the couplings: a new mechanical check or a new file class gets its row here **in the same commit** |
| **Owner** | The maintainer |

| `.claude/skills/` | The maintenance skills — [its map](../.claude/skills/README.md) | never deploys; loads in any session opened here |
| `.github/`, `.gitlab-ci.yml` | CI configs — three gating jobs in each: one calls `bin/cc-ci-check.sh` and nothing else, one runs the test suite as root in the container, one runs the dashboard's tests on the oldest Python it supports with the browser tests skipped on purpose; GitHub adds a gating job for the dashboard's browser tests (its runner has Chrome), the `deny-scan` job that does work only in a template edition (`docs/PUBLISHING.md` §4), and an informational shellcheck job. ## 3. Enforced versus discipline — read this before trusting the table

**CI-held couplings** (the numbered checks in `bin/cc-ci-check.sh`) fail the gating job on
both remotes — the same script runs on each, so there is no weaker remote to
hide behind. Trigger honesty: GitLab runs it on every branch push; GitHub runs
it on pushes to `main` and on pull requests, so a GitHub feature branch is
unchecked until its PR opens — run `bash bin/cc-ci-check.sh` by hand before
pushing, as `CLAUDE.md` already requires. What CI holds, you may lean on.

**Discipline-held couplings** are the ones git content checks *cannot* see:
whether a directory map's one-liners are still true, whether a settings row
still describes the key's real behaviour, whether a skill still matches its
section. Two backstops exist, and they are weaker than CI — treat them as
sweeps, not guarantees: the `repo-audit` skill (`OPERATIONS.md` §7.2) audits
exactly this class on request, and filesystem modes are re-asserted per
checkout by `githooks/post-merge` and `bin/cc-repo-perms.sh`, which no remote
can do ([`README.md`](../README.md), *Working on this repository*).

When a discipline coupling bites twice, promote it: a new check in
`bin/cc-ci-check.sh`, a row moved up a tier here, in the same commit.
